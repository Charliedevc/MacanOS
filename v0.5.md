# MacanOS v0.5 — hardware compatibility and deployment engineering

Branch `macanos/v0.5` begins at `a702fec` on `macanos/v0.4`. The implementation
milestone is committed locally as `ea6c7b7`; `5701ecd` includes maintenance utilities in packaged releases. No purchasing, publishing, merging,
firmware flashing, vehicle connection or factory-control modification occurred.

**Outcome:** a working desktop/kiosk deployment prototype and a documented hardware
purchase decision, with Android/ARM64 build limitations made explicit. Buy no
NaviRider or JL amplifier on the present evidence. Prefer a Pi 5 4GB removable
bench with separately specified HDMI/USB touch displays if a hardware test system
is needed. Exact head-unit compatibility is still unresolved; seller evidence and
physical acceptance tests remain necessary before an installed-system purchase.

## Implemented deployment behavior

The original `run.py` desktop workflow remains. `supervise.py` adds a simulator
kiosk mode with one backend and independently supervised driver/passenger clients.
It verifies protocol 3 and simulation, refuses a conflicting listener, restarts
only a failed process with bounded backoff and stops after a repeated short-life
failure limit. It never starts a second backend for the other frontend. Normal
window closure restarts that kiosk frontend; Ctrl+C/SIGTERM stops the kiosk.

Runtime configuration chooses each Qt screen name or observed serial selector,
fullscreen policy, logical viewport and day/night map theme. Missing/ambiguous
explicit screens hide their windows until the selection returns, preserving the
other display's process. Fullscreen roles cannot claim the same selector or omit
an explicit selector. There is no assumption that HDMI connector names match Qt
names or that serial numbers are unique.

The supervisor emits timestamped JSON events and tagged child logs, readiness
timings, current PIDs and observable state files. Qt clients now handle SIGTERM
through their event loop; the backend retains its existing graceful SQLite path.
Simulated ignition-off stops MacanOS, not the computer or vehicle. No GPIO writes,
OS power command or CAN control path was added. A real power controller/hold-up
system is still needed for electrical power removal and battery protection.

Release staging verifies SHA-256 file integrity and safe archive paths, checks
ELF architecture at packaging time, and atomically switches versioned symlinks.
Rollback selects the previous release while supervision is stopped/locked. SQLite
backup uses its backup API; settings are copied separately. These tools make no
claim to downgrade database schemas, authenticate a publisher or update an OS.
They were exercised in workspace directories, not installed into a system account.

`offline: true` is enforced in the backend navigation API, rather than only hiding
buttons: map activation is refused, online search becomes saved/coordinate search,
routing requests are disabled and update checks are suppressed. Existing licensed
offline XYZ packs and matching route-cache estimates remain possible. Neither
geographic coverage nor a regional routing graph is bundled. Other applications
and vendor firmware are outside this software's offline switch.

## Hardware abstraction and safety

| Boundary | Reused or added interface | Simulation / verification |
| --- | --- | --- |
| GPS/GNSS | Existing `LocationProvider` | Existing route replay, timestamps, accuracy/stale logic retained; no physical GNSS driver |
| OBD telemetry | Existing OCTAVE OBDManager → ParamStore/service; `DiagnosticReadPort` contract for future adapters | OCTAVE simulator remains the running source; added contract rejects write requests before its transport callback. No second OBD connection was introduced |
| Display identity | `DisplayInventory`, Qt catalog and `DisplayAssignment` | Actual Qt inventory plus file-backed simulated hotplug; physical outputs untested |
| Touch | `TouchController`, simulated affine mapping and `touch_profiles.py` | Identity/rotation/invalid-matrix tests and a mapped synthetic touch operating a real QML media button. Linux calibration rules are previewed, not installed |
| Audio | Existing `AudioOutputAdapter`, Qt and silent test implementations | New actual Qt PCM loopback test; no physical output verified |
| Ignition/power | `IgnitionProvider`, simulated provider and supervised file-event input | Simulated on/off/unknown lifecycle tested; no physical ignition adapter, host halt or vehicle actuation |

The backend/service OBD read-only enforcement remains intact. Existing DTC clearing,
write-mode and injection-denial tests pass. Read-only diagnostic queries are still
active requests, not passive CAN capture. The policy cannot constrain a third-party
CANBUS decoder or manufacturer Android service; those require their own evidence.
Factory PCM/cluster/camera/chimes/controls remain authoritative and outside scope.

## UI refinements

The v0.4 dark design system and page structure remain. Navigation now has larger
maneuver text with a simple directional symbol and distance to the next maneuver,
prominent remaining distance and an ETA clock/minute estimate. Stale, inaccurate
and off-route estimates stay unavailable, including the compact summary. No voice,
traffic, automatic reroute, lane guidance or validated road-navigation claim was
added. Simulation labels remain visible; GPS and OBD simulator speeds are independent.

The driver media column is narrower, giving the map more space. Map actions,
search/library fields, primary buttons and volume input have 48 logical-pixel touch
bounds. A day option shows the original licensed OSM tile colors; night retains
Macan Night. Theme selection is per frontend/session or deployment configuration,
not a shared backend state. Offline packs keep their native style. US/metric units,
media synchronization, backend reconnection and trip persistence remain.

Tested logical viewport matrix: **3840×720, 2560×720, 1920×720, 1920×540, 1920×480,
1280×720, 1280×480 and 960×480**, across driver plus five passenger pages in two
route states: **96 cases**. This is layout evidence, not a verified NaviRider pixel
mode, density, brightness or physical touch size. Android density can reduce the
logical viewport below the supported bounds.

### Resource and startup measurements

Final Debug desktop run: 15.08 s CPU/RSS sample, two **1920×720** windows, active
simulated route replay, local MP3, warmed raw/derived tile caches, silent test audio,
Qt Quick software/offscreen. Three logical CPUs are exposed; shared-host scheduling
is uncontrolled. No Pi/Orange Pi/NaviRider performance, power or thermal result is
inferred from this run.

| Process | CPU (% of one core) | Peak RSS MiB | Qt render interval p95 ms |
| --- | ---: | ---: | ---: |
| Backend | 5.37 | 60.54 | — |
| Driver | 18.83 | 80.64 | 2.50 |
| Passenger | 17.24 | 77.21 | 2.07 |

RSS includes shared mappings and is not additive unique memory. Render interval
is Qt `beforeRendering`→`afterRendering`, not all scene/GUI work or physical
presentation. The benchmark requests updates every 16 ms; other updates/animations
produce additional offscreen swaps (about 83/82 per second here). These are **not
hardware FPS**. Frame-swap interval p95 was 22.09/22.18 ms. Normal app runs do not
force benchmark updates. A 15 s warm-cache run is not a cold-boot/endurance test.
Machine-readable [benchmark results](v05-benchmark/results.json) and per-display
render JSON are retained.

In one staged-package lifecycle run, backend protocol readiness was **0.735 s**,
client connection/display readiness **0.735/0.730 s** and graceful application stop
**0.467 s**, with zero forced stops. These are application-launch observations on
this host, **not first valid telemetry, full map coverage or ignition-to-ready
boot time**. [Readiness events](test-results/v05-package-readiness-final.json) retain
scope/provenance. Actual SBC cold boot, wake, storage, power and thermal tests remain
on the bench checklist.

## Commands

```sh
# In this managed workspace only:
source /workspace/toolchain/env.sh
cmake --build build -j2
cmake --build build-macanos -j2
python3 macanos/scripts/run.py
# Offline kiosk with independent restarts:
python3 macanos/scripts/supervise.py --config macanos/config/desktop-kiosk.json

ctest --test-dir build --output-on-failure -j2
ctest --test-dir build-macanos --output-on-failure
python3 macanos/tests/test_deployment.py
python3 macanos/tests/integration.py
python3 macanos/tests/supervision_integration.py
npm test --prefix sdk/typescript

# Isolated audio test: normally installed PulseAudio; extracted-kit paths described below.
python3 macanos/tests/audio_loopback.py
# Explicit network provider evaluation/capture/benchmark, not offline kiosk:
MACANOS_ROUTER_URL=https://router.project-osrm.org/route/v1/driving/ \
  MACANOS_AUDIO_OUTPUT=null python3 macanos/scripts/capture.py --route
MACANOS_ROUTER_URL=https://router.project-osrm.org/route/v1/driving/ \
  MACANOS_AUDIO_OUTPUT=null python3 macanos/scripts/benchmark.py --seconds 15

python3 macanos/scripts/source_kit.py --output macanos/artifacts/macanos-v0.5-arm64-source-kit.tar.gz
python3 macanos/scripts/android_build.py --check
```

The workspace's PulseAudio was extracted under `/workspace/toolchain/sysroot`,
without installing a system daemon. Its test invocation added
`/workspace/toolchain/sysroot/usr/lib/x86_64-linux-gnu/pulseaudio` to the command's
`LD_LIBRARY_PATH` and used
`--module-dir /workspace/toolchain/sysroot/usr/lib/pulse-17.0+dfsg1/modules`.
The script creates a private socket/sink and stops its own server afterward.
Normal installations use their packaged tools without those paths.

## Remaining work and next milestone

Hardware selection is conditional, not complete installation approval. Obtain the
exact seller evidence in the compatibility matrix; validate the ARM64 native build
and real dual-output/touch/audio behavior on a removable bench. On Android, build
and sign the APK with a proper kit and prove two concurrent displays/activities,

pairing/encryption before choosing an Android/Linux network architecture.

Then diagnose the factory bass fault, measure a selected DAC/analog/digital path,
and commission a protected power/ignition/hold-up system. Complete cold boot,
thermal/crank/sleep-current and factory retention checks before any vehicle
installation. No NaviRider external video, USB touch, MOST, GNSS, factory controls
or automotive power compatibility is assumed.
